# Decisions

Decisions already made, with their reasons, so later sessions do not reopen them. Add new entries
at the bottom. To change one, add a new entry that replaces it; do not edit history.

| # | Date | Decision | Why |
|---|---|---|---|
| D1 | 2026-10-05 | UI is Avalonia, all C#, in one process. | The app must run on Windows, macOS and Linux from one codebase and look the same on each. The owner is stronger in C# than Angular. One process means no API layer between UI and git. It starts faster and uses less memory than a bundled browser. Rejected: Angular in WebView2 (Windows-only), Electron (heavy, two runtimes), OS web views (three browser engines to test), WPF (Windows-only), Blazor Hybrid (weak for a large virtualised graph). Accepted cost: the diff viewer and conflict resolver are hand-built on AvaloniaEdit. |
| D2 | 2026-10-05 | The git engine is the real `git` executable, not LibGit2Sharp. Minimum Git 2.30. | Full feature coverage (interactive rebase, worktrees, LFS, hooks, SSH, credential helpers) and behaviour identical to the command line. |
| D3 | 2026-10-05 | .NET 10. | Current long-term-support release; installed on the development machine. |
| D4 | 2026-10-05 | MVVM with CommunityToolkit.Mvvm. | Simpler than ReactiveUI and source-generated. |
| D5 | 2026-10-05 | The product is named Tracery. "Visual Git" is dropped. | The Git trademark policy restricts "Git" in product names. A search found no Git client named Tracery. Rejected: Switchyard and Branchline (Git clients with those names exist), Trellis and Ramus (crowded among developer tools). Replaced by D21. |
| D6 | 2026-10-05 | MIT licence. | Owner chose an open licence; MIT matches Avalonia and the other planned dependencies. |
| D7 | 2026-10-05 | Windows is developed and tested first. macOS and Linux run in CI; the owner tests macOS by hand later. | The development machine is Windows. The owner has a Mac but Mac testing is not the priority now. |
| D8 | 2026-10-05 | Scope is as listed in `requirements.md`. Rebase and conflict resolution get their own phase (4). | The owner accepted the suggested picks and singled out rebase and conflict solving as important. |
| D9 | 2026-10-05 | Hosting providers are GitHub, Azure DevOps and GitLab. No Bitbucket. | Owner's choice. |
| D10 | 2026-10-05 | No account, login or telemetry. Everything stays local. | A deliberate improvement over GitKraken. |
| D11 | 2026-10-05 | Every phase ends with a visual test gate: screenshots taken and each one inspected. | Owner requirement, stated as very important. The owner left the cadence open; a gate after every phase was chosen because each phase builds on the last and late bugs cost more. |
| D12 | 2026-10-05 | Visual test reports are committed; screenshots stay local in a git-ignored folder. | Keeps the public repo small. |
| D13 | 2026-10-05 | Each phase is built on its own branch and merged into `master` after the owner accepts it. Nothing is pushed. | The owner asked for work to be committed and will push to their own GitHub account themselves. The "nothing is pushed" part is replaced by D23. |
| D14 | 2026-10-05 | One phase per session. All context passes through the repo: `CLAUDE.md`, `status.md`, `architecture.md`, `decisions.md` and a handoff per phase. | The project does not fit in one session, and a new session remembers nothing from earlier ones. |
| D15 | 2026-10-05 | Expected results for visual checks are written and committed before the UI they test is built. | Otherwise a session could write expectations to match whatever it built, and the gate would prove nothing. |
| D16 | 2026-10-05 | The real-window pass uses an in-repo harness on Windows UI Automation (FlaUI). | It must not depend on the tools a particular session happens to have. Phase 0 proves it works; a fallback is agreed with the owner if it does not. |
| D17 | 2026-10-05 | CI is reported as unverified until the owner pushes the repo. | Sessions never push, and the repo has no remote yet. Replaced by D23. |
| D18 | 2026-10-05 | Accepted phases are merged with `git merge --no-ff`. | Each phase stays visible as one unit in the history. |
| D19 | 2026-10-05 | The real-window pass is its own project (`VisualCommit.RealWindowTests`): Windows-only, opt-in, never in the default test run or CI. Tests always use a temporary data folder (`VISUALCOMMIT_DATA_DIR`). | Every session runs the default tests at start-up. They must not take over the mouse, fail on macOS or Linux, or overwrite the user's real settings. |
| D20 | 2026-10-05 | The main window follows the layout table in `requirements.md`: tabs, toolbar, left panel, graph, right panel, status bar. Proposed by the planning session; the owner has not reviewed it yet. | Visual checks need a written layout to be compared against. It follows the familiar GitKraken arrangement, with the app's own styling. |
| D21 | 2026-10-06 | The product is named VisualCommit. Replaces D5. Identifiers follow: `VisualCommit.*` projects, `refs/visualcommit/backup/`, `VISUALCOMMIT_DATA_DIR`. The identifiers in D19 were updated to match. | Owner's choice. The name has no "Git" in it, and a search found no existing product called VisualCommit. |
| D22 | 2026-10-06 | The main window layout in `requirements.md` is accepted. Completes D20. | The owner reviewed it and agreed. |
| D23 | 2026-10-06 | Sessions push commits to `origin` (github.com/RahimPasha/VisualCommit). CI results are read from GitHub and reported as they are. Replaces the "nothing is pushed" part of D13 and replaces D17. No force-pushes or rewriting of pushed history; other changes on GitHub (settings, visibility, releases) are asked about first. | The owner created the repo and said sessions may push. Pushing lets CI cover macOS and Linux from phase 0 on. The limits in the last sentence are the planning session's own caution, not an instruction from the owner. |
| D24 | 2026-10-06 | Tests use xunit.v3 3.2.2 on Microsoft Testing Platform (`global.json`), not the newest xunit.v3 (4.0.1). | Avalonia.Headless.XUnit 12.1.3 is built against xunit.v3 3.2.2 and cannot discover tests with 4.x (a method it calls is gone). On the .NET 10 SDK, `dotnet test` with xunit.v3 needs the Microsoft Testing Platform runner. Move xunit and Avalonia.Headless.XUnit together when Avalonia supports a newer xunit. This is the one package not at its latest stable release. |
| D25 | 2026-10-06 | `VisualCommit.RealWindowTests` is kept out of `VisualCommit.slnx`. It has its own command. Carries out D19. | `dotnet build` and `dotnet test` at the repo root work on the solution, so leaving the project out is what keeps the real-window pass from ever running by default, in CI, or on macOS and Linux, where it could not even build. |
| D26 | 2026-10-06 | The log is a small file logger of our own (`FileAppLog`): one file per day, 14 days kept. No logging library. | The app needs a few lines per git call and per error. A library would add a dependency and configuration for no gain. `IAppLog` in Core is the seam if that changes. |
| D27 | 2026-10-06 | Icons are outlines from Lucide (ISC licence), drawn as strokes by our own `Icon` control. `THIRD-PARTY-NOTICES.md` lists them. | A toolbar needs icons, and drawing a consistent set by hand is not this project's job. Lucide is open, permits this use, and its plain stroke style is not GitKraken's look, so R5 is kept. |
| D28 | 2026-10-06 | The app uses the Inter typeface that ships with Avalonia on every platform, not the system font. | Q6 asks for the same look on Windows, macOS and Linux, and screenshots from the three CI platforms can then be compared. |
| D29 | 2026-10-06 | Theme colours are tokens in `Theme/Tokens.axaml`, one set per theme, used only through `DynamicResource`. The accent is indigo. The token table is in `architecture.md`. | Switching the theme must recolour everything at once, and visual checks need named colours to compare against. Indigo keeps clear of GitKraken's teal (R5). |
| D30 | 2026-10-06 | Every git call runs with `LC_ALL` and `LANG` set to `en_US.UTF-8` and `GIT_TERMINAL_PROMPT=0`. | Git's messages must be the same on every machine to be parsed and tested, and git must fail rather than wait for a terminal that is not there. Phase 3 replaces the prompt setting with in-app dialogs (C11). |
| D31 | 2026-10-06 | Cancelling a git call stops git and everything it started; on Windows through a job object. After git exits, its output is read for at most 2 more seconds. | Found by the runner's tests: on Windows the children of git's bundled shell (hooks, aliases, ssh) escape a kill by process tree, and a process git leaves behind keeps the output pipes open, so the call would hang until that process ends. The job has no kill-on-close limit, so helpers meant to outlive a call (the file-system monitor) survive a call that completes. |
| D32 | 2026-10-06 | In the scripted walk-through a "restart" runs the second app instance with a new Avalonia `Application` object in the same test process (`FreshApplication.RunAsync`). The real-window pass restarts the real process. | Headless tests cannot start a second process cheaply, and a new `Application` exercises the whole start-up path. The real-window pass covers the true process restart. |
| D33 | 2026-10-06 | A real-window screenshot "matches" the scripted one when at most 3% of its pixels differ after scaling it to the scripted size, and it is also inspected by eye. | Gives the comparison in the visual gate a number. Text edges differ between the two renderings (about 0.65% of pixels at 200% scaling); a wrong theme or a missing region differs far more. The number does not replace inspection: one missing line of text is well under 3%. |
| D34 | 2026-10-06 | CI does not run for pushes that change only docs. It uploads the scripted walk-through's screenshots from each platform. | The repo is private, so CI minutes are limited and macOS minutes count ten times; status and report commits would spend them for nothing. The uploaded screenshots are the only look at macOS and Linux rendering until the owner tests on a Mac. |
| D35 | 2026-10-06 | Every default test assembly carries `[assembly: HangWatchdog]`: a test that runs over 3 minutes, or a run in which nothing happens for that long, ends the test process and prints the tests that were running. | A CI run hung on macOS and left no log, so nothing said which test was stuck. A hang must fail quickly and name itself. |
| D36 | 2026-10-06 | Stopping git never throws, always ends with a plain kill of git itself, and a cancelled call returns after 10 seconds even if git is still there. Extends D31. | The process-tree kill is not all-or-nothing: on macOS and Linux it suspends each process before it lists the children, so a failure half-way leaves git suspended, alive and holding its pipes, and the call that waits for it would never return. |
