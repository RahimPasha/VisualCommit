of the phase and before the UI they test was built (D15), from `requirements.md`, `plan.md`, the

### Part A: the menus, the keyboard, double-click, drag, the toolbar and ignoring a file

Part A of the phase 3 visual test report, written before the UI it tests from `requirements.md`,
`plan.md`, `docs/phase-3-design.md` (2, 4a to 4h, 5, 6.3, 6.5, 7.1, 7.5) and decisions D77 to
D115. It covers the context menus of every object with their disabled items and tooltips, the
keyboard in menus, the menu's placement and light dismiss, double-click actions, dragging a branch
onto a branch, the toolbar with a repository, the left panel's selection following the graph's,
and ignoring a file. Every git state below was derived with plain Git 2.36.0.windows.1 on
repositories built exactly as `Scenarios.Phase3.cs` builds them, each operation run as design
section 2 says the app runs it.

Conventions:

- **Commits** are named by their subjects. A commit of a scenario repo is also given by its short
  SHA (its first 7 characters) where a text on screen shows it; those SHAs are the ones
  `ScenarioTests` pins. A commit the app makes is named by its subject only, except where its id
  is stated as the one plain git gives for the same commit. Refs are named by their short names.
- **Times** are UTC. A scenario repo's commits and stashes are dated by `TempRepo`'s clock:
  2026-01-01 12:00 plus one minute per commit, stash and merge; a copy carries on from its
  template's clock (an ops copy is at 12:08). Commits and stashes the app makes are dated
  2026-01-02 09:00, with the identity "Test Author" <author@example.com> the repo keeps in its
  configuration (D72).
- **Lanes** count from 0 at the left; **colours** are lane colour numbers, as in phase 1's table
  (dark: 0 `#7C8CFF`, 1 `#3FB97F`, 2 `#E0A23B`, 3 `#E5606B`, 4 `#4FB3D9`).
- **Menus** are written header first, items in order, "—" for a separator; "(danger)" marks an
  item drawn in `VcDangerBrush`, "(disabled: "…")" a disabled item with its tooltip. "Highlighted"
  means the `VcHoverBackgroundBrush` background of the item that has the focus.
- **Resting the pointer** on an item, button or row means moving it there in one move, without
  crossing other menu items, and leaving it still for 1 second (Avalonia shows a tooltip after
  about 0.7 s).

#### What phase 3 must show: the menu and the toolbar

##### The menu (4a, D105), as every check here asserts it

- **What draws it.** Avalonia's `MenuFlyout` on the window's overlay layer: inside the main window, above the panels and under the dialog layer, never a window of its own. At most one is open.
- **UI Automation.** The container is `ContextMenu` (control type Menu), the header `ContextMenuHeader` (control type Text, named by its full text). Each item is a `ContextMenuItem` (control type MenuItem), named by its label, with `IsEnabled` as drawn, the Invoke pattern, and a disabled item's reason as its `HelpText`.
- **Look.**
  - Background `VcPanelBackgroundBrush` (`#1A1D24` dark, `#F5F6F8` light), a 1-pixel `VcBorderBrush` border, corners rounded by 6, padding 4, and the `VcMenuShadow` shadow.
  - Width 200 to 360, set by the longest label.
  - The header row is 24 high, its text in `VcTextSecondaryBrush` (`#9BA3B0` dark), cut with "…" past 340, the whole text in its tooltip. A click on it does nothing and keeps the menu open.
  - An item is 26 high, with 10 px of padding at each side. A separator is 9 high, with a 1-pixel line.
  - So a menu that fits the window is 8 + 24 + 26 × items + 9 × separators high (±2).
- **Item colours.**
  - Item text is in `VcTextPrimaryBrush` (`#E4E7EC` dark).
  - An enabled destructive item, marked "(danger)", is in `VcDangerBrush` (`#E5606B` dark).
  - A disabled item, a destructive one too, is in `VcTextDisabledBrush` (`#5F6775` dark) (D114). Its reason shows as its tooltip, inside the window, when the pointer rests on it; a reason that a step does not picture is asserted through the item's `HelpText`.
  - The highlighted item has `VcHoverBackgroundBrush` (`#2F3542` dark).
- **Highlight and focus (D105).** When a menu opens, however it was opened, the focus moves into it and its **first enabled item is highlighted**; every menu screenshot shows that. A menu with no enabled item shows none highlighted. Down and Up move to the next or previous enabled item, wrapping and skipping the header, separators and disabled items; Home and End go to the first and last enabled item; Enter or Space invokes; Esc closes it and gives the focus back to the element focused before. Moving the pointer over an enabled item highlights it and moves the focus there; a disabled item takes neither.
- **Placement.**
  - Opened by the pointer, its top-left corner is 2 right of and 2 below the pointer.
  - When it would cross the window's right edge it opens to the left of the pointer (its right edge 2 left of it); when it would cross the bottom it opens above it (its bottom edge 2 above it); then it is moved to stay 4 px inside the window.
  - Opened by the keyboard (Shift+F10 or the Menu key), it opens at the bottom-left corner of the focused row: in the graph the selected row's message cell, in the left panel the focused row.
- **Closing (light dismiss).** A press of any mouse button outside the menu closes it and is not passed on; so do Esc and the window losing activation. It also closes when a dialog opens, the active tab changes, or the wheel turns anywhere in the window. Invoking an item closes the menu first, then runs the item.
- **Opening.** A right-click, the Menu key, or Shift+F10 (D106: one menu per press on every platform). The menu layer logs `<repo>: Context menu opened: <header> by pointer` or `… by keyboard` at Debug for each menu. The first menu of a process can take up to about 2 s to appear; both harnesses wait for it, never for a fixed time.
- **What a right-click selects (4b, D114).** A right-click on a graph row or on a label in the graph selects that row. A right-click on a left-panel row (branch, remote branch, remote, tag, stash) or on a file row opens the menu only: nothing is selected or highlighted, and the graph's selection does not change.
- **How the lists below read.** A group whose items are all left out leaves no separator behind: a menu never shows a separator right after its header, at its end, or two in a row (D114).
- **Later phases.** Their items (rebase, squash, compare, file history, blame, create pull request) appear in no menu, neither enabled nor disabled (D77, D92).

##### The toolbar with a repository (4d)

Fetch, Pull, Push, Branch, Stash and Pop are enabled or disabled according to the active tab's repository:
- An enabled button draws its icon and label in `VcTextPrimaryBrush`, a disabled one in `VcTextDisabledBrush`.
- A disabled button's tooltip gives its reason (`ToolTip.ShowOnDisabled`), drawn inside the window.
- Undo, Redo and Search stay disabled placeholders with no tooltip. Theme works as in phase 0.
- A tab without a repository is as in phase 0: only Theme is enabled, and there are no tooltips.

Where several reasons hold, the tooltip gives the first in 4d's order of that button's conditions (design 2, "Several reasons"). The conditions, in that order, and their tooltips (`<b>` the current branch, `<r>/<u>` its upstream, `<kind>` the operation in progress):

| Button | Conditions, in order, with their tooltips |
|---|---|
| Fetch | no remotes: "This repository has no remotes" |
| Pull | detached: "HEAD is detached: check out a branch to pull"; no upstream: "<b> has no upstream: set one first"; a gone upstream: "<r>/<u> no longer exists"; an operation in progress: "Finish or abort the <kind> first"; no remotes, unless the upstream is local: "This repository has no remotes" |
| Push | detached: "HEAD is detached: check out a branch to push"; HEAD unborn: "Make the first commit first"; no remotes: "Add a remote first"; a local upstream: "<b> tracks a local branch" |
| Branch | HEAD unborn: "Make the first commit first" |
| Stash | HEAD unborn: "Make the first commit first"; nothing to stash: "There are no changes to stash" |
| Pop | no stashes: "There are no stashes" |

### Part D: remote operations, credentials and prompts, remotes, the light theme and closing the window

Part D of the phase 3 visual test report. It was written before the UI it tests, from
`requirements.md`, `plan.md`, `docs/phase-3-design.md` (sections 1.8, 1.9, 2, 2.33, 3, 4a to 4h,
5, 7.1 to 7.5) and decisions D77 to D115. It covers:

- fetch, with its progress, Cancel and the lock files a cancel can leave;
- pull, push, a rejected push and force push with lease;
- the credentials dialog and the ssh prompt dialogs;
- the Remotes dialog, setting and removing an upstream, pushing a branch without an upstream and
  pushing a tag;
- fast-forwarding a branch that is not checked out, and deleting a branch on a remote;
- a menu, the reset dialog, the conflict banner and the error dialog in the light theme;
- closing the window while a fetch runs.

Every git state and text below was derived with Git 2.36.0.windows.1. The repositories were built
exactly as `Scenarios.Phase3.cs` builds them, and the short SHAs they gave are the ones
`ScenarioTests` pins. Each operation was run as design section 2 says the app runs it. An HTTP
server behaved as `AuthRemoteServer` does: `git http-backend` behind Basic auth, the 401 body
"Authentication required.", and the hold of the next fetch pack.

Conventions:

- **Commits** are named by their subjects. A scenario commit also gets its pinned short SHA (its
  first 7 characters) where a text on screen shows it. A commit the app makes is named by its
  subject only.
- **Times** are UTC and come from three clocks:
  - A scenario repo's commits and stashes are dated by `TempRepo`'s clock: 2026-01-01 12:00
    plus one minute per commit, stash and merge. A copy carries on from its template's clock, so a
    sync copy's next commit is at 12:05.
  - `Scenarios.PushFromElsewhereAsync` commits at the next minute of sync's clock. A step "outside
    the app" goes through `TempRepo` on that clock too, as a terminal would.
  - Commits the app makes, and the ref updates of its git calls, are dated 2026-01-02 09:00, by
    "Test Author" <author@example.com> (D72).
- **Lanes** count from 0 at the left. **Colours** are lane colour numbers, as in phase 1's table
  (dark: 0 `#7C8CFF`, 1 `#3FB97F`, 2 `#E0A23B`, 3 `#E5606B`, 4 `#4FB3D9`). A "+1" next to
  `main` (check mark) is the pair that phase 1's check 13 showed: `main` with its check mark and
  `origin/main` behind "+1". Where the other labels of a row are listed without a "+N", phase 1's
  "+N" rule decides how many fit.
- **Menus** are written header first, then the items in order, with "—" for a separator.
  "(danger)" marks an item drawn in `VcDangerBrush`, and "(disabled: "…")" marks a disabled item,
  drawn in `VcTextDisabledBrush`, with its tooltip. When a menu opens, its first enabled item is
  highlighted (`VcHoverBackgroundBrush`) and has the focus (D105); every menu below says which
  item that is.
- **Pointer and right-clicks.** A right-click on a left-panel row opens its menu only: nothing is
  selected or highlighted, and the graph does not change (D114). **Resting the pointer** on an
  item means moving it there in one move, without crossing other menu items, and leaving it still
  for 1 second.
- **Texts.** Titles, running texts, error dialog titles and summaries are design 2.33's (D113).
  The status bar shows "<Title> failed" in `VcDangerBrush` and "<Title> cancelled" in the
  secondary colour (4e). Counts use the singular for one.
- **The error dialog** (`ErrorDialog`, a card 400 wide on the backdrop) shows, top to bottom:
  - its title;
  - `ErrorSummary`;
  - `ErrorRepository`: "In <repo>", always shown;
  - `ErrorOutput`: git's output, cleaned as `GitOutputCleaner` does (design 1.6), in the code font.
    Line ends are trimmed, leading spaces are kept (` ! [rejected]`), and empty lines and progress
    lines with a percentage are dropped;
  - `ErrorCommand`;
  - the buttons "Copy output" (`ErrorCopyButton`), the extra button if there is one
    (`ErrorExtraButton`) and "Close" (`ConfirmButton`).
- **Other dialogs.** Every check has one repository tab, so no other dialog shows a "In <repo>"
  line (4f).
- **The server.** Checks that need a server use `AuthRemoteServer.StartForVisualChecksAsync()` on
  127.0.0.1:47391. When that port was taken (`PortWasTaken`), the pictures differ in the port
  only, and the report says so.
  - **Sync at the server.** Checks 18, 18b, 19, 20 and 22 point sync's `origin` at
    `http://127.0.0.1:47391/origin.git` before the app starts. With `RequireAuth = false`, the
    server serves sync's own `origin.git` in place (design 7.3), so `PushFromElsewhereAsync` still
    pushes into what the app fetches. Git's `To` and `From` lines and the pull's merge subject
    then read the same in every run.
  - **Folder remotes.** Checks 28, 29 and 30 use the scenarios' folder remotes, because nothing
    they show names a remote's path.
- **Percentages.** A held fetch shows the stage and percentage of the last progress line git
  printed before the hold. The check accepts any N from 1 to 100 and names the value Git 2.36
  gave.
- **Waiting.** "Wait until idle" means `ShellDriver.WaitForIdleAsync`: the queue is idle and its
  refresh is done. The real-window pass instead waits for the queue's log line,
  `<repo>: <Title>: <outcome> after <N> ms`.

## How the expected git states were derived

**Part B.**

- Each operation was run as design section 2 says the app runs it, with the harness's dates (D72), on a scenario rebuilt as `TempRepo` builds it:
  - **Merges:** `git fmt-merge-msg`, then `git merge --no-edit --no-log -m <message> [--no-ff] <full ref>` (2.8, 2.9, D94).
  - **Resets:** the backup batch (`git update-ref --stdin` with `create` lines), then `git reset --soft`, `--mixed --quiet` or `--hard` (2.0, 2.11).
  - **The hard reset's snapshot:** a temporary index read from HEAD plus the listed paths, with a commit of the real index's tree as a second parent (2.11).
  - **Picks and reverts:** one `git cherry-pick <sha>` or `git revert --no-edit [-m 1] <sha>` per commit (2.12 to 2.14).
  - **Aborts:** `abort-<time>` and D67's snapshot of the changed files, then `git merge --abort`, `git cherry-pick --abort` or `git revert --abort` (2.15).
  - **Checkouts:** `git switch --no-guess` and `git switch --detach` (2.1, 2.3).
  - **The stage panel's commit** (check 9b): `git add`, then phase 2's `git commit --file=- --cleanup=whitespace`.
- 7.1 gives no colours, so G0 adds them by D48: Alpha's lane takes colour 3, because colour 2 went to "Fast-forward me".
- `git fmt-merge-msg` prints nothing for a branch that is already merged. The merge then says "Already up to date" (check 8 step 9), and the empty message is never used.
- During a merge, `git switch` fails with `fatal: cannot switch branch while merging` and `Consider "git merge --quit" or "git worktree add".` (exit 128), as design section 0 records; it is an "other failure" of 2.1.
- A merge the app starts names the full ref in the conflict marker (`>>>>>>> refs/heads/feature/conflict`). One started in a terminal names the short name (`>>>>>>> feature/conflict`, `StoppedAsync(Merge)`). Both `MERGE_MSG`s start with "Merge branch 'feature/conflict'", so the banner is the same.
- In `EdgeCasesAsync` a local branch is named `origin/main`, so after checking out `main`, `git status --short --branch` names the upstream `remotes/origin/main` to tell it apart.

All of it was derived with Git 2.36.0.windows.1 on the development machine. CI runs Git 2.55: a
check whose expected text is git's own message is checked by the unit tests of phase 3's Git layer
on both versions.
